## 代理路由修复与复测

排查发现本机 macOS 配置了 HTTP/HTTPS 系统代理，但没有代理环境变量。早期成功的临时 Python 转发使用 `trust_env=True`，读取了系统代理；原生 OpenCode 以及后来 `trust_env=False` 的传输对照未沿用这条路径。因此，早先把差异集中在 HTTP 客户端上的解释不充分。

接入现在在没有显式代理变量时读取系统代理，仅传入 OpenCode 子进程；已有代理变量和明确空值优先保留，并补充回环地址的代理排除项。FlowCanvas 访问自有工作流宿主时则强制直连。一个拒绝请求的本地代理先使原来的宿主检查失败，修复后同一检查通过。OpenCode 的代理变量与本地绕行方式符合其 [网络配置说明](https://opencode.ai/docs/network/)。

修复后的默认模型完整执行在 70.246 秒内通过：验证实际摘要、宿主完成回执、RTL 未修改、`Exit` 返回成功和原生轮次完成。这个通过样本证明本机原有代理路径可以支撑完整流程；不把一次成功扩展为所有网络条件下的稳定性保证。

## 修复前的诊断记录

同一完整工作流在三次直连检查中达到 600 秒上限而失败，分别耗时 603.773 秒、603.260 秒和 603.326 秒（含清理）。其中两次已完成源码读取与摘要写入，但未走完验收；另一次在约 7 分钟后启动工作流，随后原生会话报告连接异常并重试。超时时 FlowCanvas 没有未返回的 MCP 调用。第三次诊断确认原生最后一条 assistant 消息尚无输出片段，之前的工具均已返回。

后续临时转发观测使用原配置的模型服务与凭据，只记录请求大小、推理档位、状态和时序，不记录请求正文、回复正文或凭据。该样本的响应均正常完成，证明这一次完整执行链可以通过；它改变了 HTTP 传输路径，不能据此宣布直连问题已修复，也不能用成功样本覆盖先前失败。

这些诊断使用 OpenCode 原生连接模型服务，没有加入正式转发层、改写用户配置或放宽验收。后续代理路由检查解释了其中一项关键环境差异，以上失败样本仍保留。

进一步检查自有测试进程的原生日志，发现第三次直连期间有两次模型请求报 `ECONNRESET`，随后重试。请求使用的推理档位仍为 `low`，没有证据表明等待来自错误的档位设置。原生事件的会话字段也与本机 API 定义一致，未发现因事件归属丢失而只能在结束时补齐的情况。

随后仅在临时测试进程设置 `BUN_FEATURE_FLAG_DISABLE_IPV6=1` 做对照，确认模型连接使用 IPv4，但完整工作流仍达到 600 秒上限而失败（含清理 603.350 秒）。它已完成工作流启动和源码读取，后续等待期间没有未返回的 MCP 调用。因此，强制 IPv4 不足以解决本机的直连问题；该设置未加入正式接入或用户配置。

另用相同的单次 MCP 查询比较默认连接与临时项目中的 `Connection: close` 请求头，两者均未在 120 秒内完成。默认连接的工具已返回，但最终模型回复仍在等待；禁用复用的样本尚未返回工具调用。这个对照没有支持把禁用连接复用作为修复，相关设置也未保留到正式配置。

临时诊断插件随后观察了原生 `fetch`：一次请求约 12 秒后收到 HTTP 200 和首批流数据，但 180 秒内没有完成。在同一时段，将下一次请求的同一正文分别交给原生 `fetch` 和 Python HTTP 客户端；两者都收到 HTTP 200，仍分别在 180 秒和 170 秒的观察上限内未完成。原生会话中也没有对应的 assistant 消息片段。这说明先前转发样本的成功不足以证明更换 HTTP 客户端可以解决问题，仍需核对服务返回的流格式及其时段性表现。

事件形状检查捕获到 `codex.rate_limits`、`codex.response.metadata` 的完整数据，以及 `response.created` 的 SSE 事件名称，但在 180 秒内没有观察到对应的完整数据包或终止事件；这不是已经取得完整回复、只是网页未显示的情况。诊断插件只存在于临时项目，记录时间、状态、数据长度和事件类型，不保存正文或凭据。

随后从已发现的模型目录选择 `opencode/big-pickle`，通过相同的真实工作流检查。原生直连在 257.045 秒内完成，实际摘要、验收回执、未修改 RTL、成功的 `Exit` 和原生轮次结束均通过断言。这支持接入链路可以在另一个模型上完整执行，但不能代替用户默认 `sub2api/gpt-6.1-sol` 的稳定性复核，也不代表执行速度已达到理想体验。选择仅发生在临时测试进程，正式默认值未变。

## 已修复的交接状态问题

完整新增用例实测曾出现一次 `test_cases(guide)` 返回 `Not connected`，随后模型继续任务。独立的真实 CLI 与本地服务检查将它固定复现：模型请求已经准备好工具后再刷新 MCP，原调用在该时序下报连接错误。[原生 MCP 实现](https://raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/mcp/index.ts)在注册替代客户端时关闭旧客户端，而已准备的工具保留旧客户端引用。现在活动轮次和关闭过程中不重新注册 MCP，新增阶段工具通过现有轮次交接加载；空闲时仍正常刷新。回归验证原工具成功和下一轮新工具可见。这只是修复连接被打断的问题，[提案 05](proposals/05-workflow-startup.md)所建议的提前准备仍未实施。

空闲刷新与新发送也需要协调：确定性检查复现刷新请求还未返回，新提示已经交给原生执行。刷新现在与请求交付串行化，新请求等客户端替换完成后再发送；启动期间的首次连接沿用生命周期锁，避免与发送失败收尾形成反向锁顺序。修复后的完整回归与真实工具调用检查均通过。

直连复测还暴露了一个独立问题：原生轮次结束、工具目录等待自动重连时，宿主仍活着，卡片却被标为暂停。现在内部交接保留运行状态，实际用户停止、切为只读或宿主退出仍会暂停。回归先复现了原问题，再验证修复及上述边界；这项修复不改变模型请求速度。

执行连接意外断开时，原逻辑只更新对话状态，未统一收尾进行中的条目、暂停队列和立即保存结果。断连现在复用失败轮次的收尾逻辑，保留部分内容与已完成的工具结果。确定性检查先复现问题，再验证 Codex 和 OpenCode 的会话隔离、持久化与队列暂停；真实 OpenCode 进程退出检查进一步验证了原生历史恢复。这项检查没有在运行中的外部命令上终止进程，不据此推断所有工具子进程的退出行为。

另用本地 HTTP 服务发送较大的工具事件，复现了事件读取任务因客户端默认行长上限而退出的问题。本机 aiohttp 的上限为 524,288 字节；超过该值的单行 SSE 数据会抛出 `LineTooLong`。接入现改为按字节块拼接完整协议行，再解码和处理事件，保留跨块 UTF-8 与多行 SSE 数据。回归验证大输出原文完整、后续消息正常、没有重连或额外历史请求；真实模型事件流恢复也再次通过。这里的大输出来自协议测试服务，不是声称已用模型生成同等大小的日志。

连续轮次检查还复现了上一轮消息误归当前轮次的问题：迟到的旧正文快照与增量可以进入新轮次，旧 assistant 错误也会结束或中断新轮次。适配器现在根据原生父消息与历史中的用户消息边界记录归属；执行中追加要求和压缩续写生成的用户消息仍归属同一次 FlowCanvas 任务。用于确定归属的查询只索引元数据，不提前投影正文，避免与缓冲中的增量重复。八种旧事件组合先全部失败，再通过修复验证；另检查续写文本不重复，以及归属查询期间切换轮次的隔离。原生父消息关系依据 [OpenCode 的消息创建实现](https://raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/session/prompt.ts)；真实多轮检查也验证了执行中引导仍能完成。

真实自动压缩检查进一步复现了内部摘要被当作普通回复显示的问题。原生摘要已正常完成，但最终聊天投影多出了一整段用于后续上下文的摘要。现在普通事件、断线恢复快照和子会话预览都不显示内部摘要；子会话也不显示原生自动续写指令。用量和错误仍按原生命周期处理，压缩失败不会被隐藏成成功。确定性回归覆盖正文、推理、恢复、失败与子会话；同一真实自动压缩检查随后通过，关键要求和正常续写均保留。

服务返回的上下文超限与普通终止错误有不同语义。[原生处理器](https://raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/session/processor.ts)会先发布超限事件，再决定启动压缩或记录终态错误。原接入在第一个事件处取消了任务，阻断自动恢复。现在这类会话事件交给原生继续处理，只有 assistant 记录中的实际错误才作为失败；禁用压缩和摘要自身超限仍会报告失败。真实 CLI 与本地 HTTP 夹具先复现提前取消，再验证三条路径；它验证的是协议和生命周期，不是外部服务容量或摘要质量。

本机默认 `sub2api/gpt-6.1-sol` 的原生模型元数据为 `limit.context: 0`、`limit.output: 0`。根据 [原生阈值实现](https://raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/session/overflow.ts)，上下文上限为零时不会按用量阈值提前压缩。本次测试只在临时项目补充上限并缩小阈值，未更改用户模型配置，也未推测该服务的实际容量；它验证自动压缩与适配续写路径，不代表默认配置已经具备主动阈值压缩。

用量字段也需要转换语义。[OpenCode 原生计数实现](https://raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/session/session.ts)为分别计价，从输入中扣除缓存读取和写入，从输出中扣除推理；[OpenAI 用量说明](https://developers.openai.com/api/docs/guides/agents-api/observability#understand-token-usage)的输入与输出则分别包含这些子项。适配器现在将分类加回对应总数，并保留缓存写入明细；原生 `total` 存在时直接保留，缺少时才按分类求和。事件与恢复快照共用转换，内部压缩消息的用量也能恢复。确定性检查覆盖缓存写入、缺失总数、明确零值和缺失用量；真实 CLI 夹具验证缓存读取、推理及事件遗漏。这里的 `usage.last` 仍来自一条原生消息，不是任务累计；没有定价元数据时原生 `cost` 可为零，不据此推算实际账单。当前前端没有 token 展示，本次未添加界面或实现提案 22 的任务预算。

正常关闭检查还发现，只结束 OpenCode 服务进程会留下它启动的本地命令继续运行。关闭现在先在 HTTP 连接可用时取消本适配器拥有的活动会话，再关闭连接和进程。每次取消有时间上限；取消无法确认时仍清理其他资源，并将该对话保存为错误，而非成功中断。工作台关闭也统一收尾活动条目、任务卡与结束时间，并暂停队列。真实检查先观察到关闭后临时命令仍存活，修复后确认父子进程退出且心跳不再变化。测试只涉及临时本地命令，不等同于远端 SSH 任务或强制结束工作台进程的回收保证。

停止请求原先也会在工作流暂停或子会话查询失败后提前返回，漏掉父任务取消；某个子会话中断失败还会跳过其余子会话。现在逐项尝试清理，汇总未确认的取消错误，并通过统一终态处理保存部分输出、任务卡和暂停队列。迟到的运行或完成事件不能抹掉该错误；建立连接期间出现同类错误也不会继续发送请求。Codex 与 OpenCode 的这些边界由确定性检查覆盖；真实 OpenCode 命令检查进一步验证查询故障后的父任务退出，不据此声称未知子任务均已成功取消。

发送阶段的本地等待被取消时，还会提前清除活动记录，使随后的正常关闭漏掉原生取消。现在本地协程取消不释放原生任务归属，关闭流程仍能向它发送取消并清理进程。[原生异步入口](https://raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/server/routes/instance/httpapi/handlers/session.ts) 会启动独立执行后返回接收响应，因此本地调用是否已经返回，不能作为原生任务是否存在的依据。测试保留真实请求与命令，仅延迟调用返回来固定这个边界；修复前的检查失败，修复后验证了实际命令退出、历史未重发和队列未继续。

普通发送和引导的接收响应丢失时，原处理也会丢弃活动归属，或者把已经完成的结果改成失败。两类请求现在都使用明确的原生消息 ID；异常后只查询该 ID，不重发模型请求。真实检查还发现接收响应与消息落盘之间存在短暂间隔，因此确认会在 10 秒内重复读取同一记录。超过这个范围仍无法确认时，先尝试原生取消与连接清理，再记录失败；取消也无法确认时保留该说明。共用聊天服务同时保留已经收到的终态，并在引导交付期间继续排队新消息。确定性检查先复现丢失归属、覆盖终态和排队竞争，再通过修复；真实检查验证了两条请求各自只存在一份。

引导尚未送达时，原回复结束还可能先产生一次原生空闲。此前只检查原请求存在和会话空闲，会过早结束任务，后来的引导回复不再显示。现在提交引导前先记录最新输入，核对它已落盘、最后一条用户消息已有完整的最终回复，再结合原生空闲判定完成；等待期间输入改变也会使旧判定失效。工具调用回合、未完成回复及内部摘要均不作为最终回复。这与 [原生执行循环的父消息和结束状态判定](https://raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/session/prompt.ts) 对应。真实延迟引导检查先复现、再通过修复；自动压缩与续写随后也通过复测。

停止与引导交付也存在次序问题：取消先返回、引导后到达时，原生会话会重新开始执行。发送与取消现在串行化，停止先封闭新引导入口，再等待已交付中的请求返回并发送原生取消；等待期间的空闲事件不能提前结束任务。公共 HTTP 接口也在等待工作流清理之前标记停止中，Codex 和 OpenCode 均拒绝此后新增的引导，并保留原队列。确定性检查和实际 OpenCode 检查都先复现、再验证修复；真实命令树停止也通过复测。该检查固定的是适配器到原生服务的请求交付时序，不代替原生内部全部准备阶段的取消验证。

后续检查进一步复现了原生内部的准备窗口：[原生 prompt 实现](https://raw.githubusercontent.com/anomalyco/opencode/v1.19.5/packages/opencode/src/session/prompt.ts)先准备和保存消息，再进入可取消的执行循环。测试用临时 MCP 资源读取固定这个窗口，确认接收响应已经返回、消息还未保存；此时原生取消返回空闲，释放准备后仍会启动模型。停止和失败收尾现在都在原生取消后回收该对话的执行进程，已有历史继续由新连接恢复。这个资源附件只用于延迟注入，没有给正式聊天增加附件接口，也没有修改用户项目。真实命令停止、原生错误恢复、上下文恢复和重试六种服务场景均随之复测通过。

连接回收还需要与重新连接串行化。确定性检查复现了旧进程等待退出期间，观察请求提前替换进程和客户端的问题；现在两者共用生命周期锁，旧资源释放后才建立新连接。事件读取任务仍可清理自身拥有的连接，不会取消或等待自身。

原生报错同样不能立即释放还有请求在交付的任务。会话错误、消息错误和恢复快照现在共用失败收尾：阻止新引导，等待已开始的交付结束，取消原生执行并回收该对话的执行进程后再发布失败。取消接口异常时继续尝试清理连接；无法确认取消则保留说明，始终保留原始失败原因。事件读取任务可以发起自己的连接清理，但不会取消或等待自身。三个错误入口均先通过确定性检查复现，再验证修复；真实 CLI 配合本地 HTTP 错误与流式响应夹具，也验证了迟到执行被取消、原生历史保留和下一轮恢复。该夹具只产生本地测试响应，不作为外部模型服务稳定性的样本。

另通过公共聊天 API 检查原生重试：本地服务返回 HTTP 503 和短重试间隔，真实 CLI 负责重试，工作台没有额外提交用户消息。恢复时任务持续运行，最终成功会清除错误；停止会取消尚未触发的原生重试，耗尽则保留真实服务错误，两者都暂停后续队列。恢复中的增量回复已经显示时，旧重试错误仍会暂留到终态，这是 [状态展示提案](proposals/15-execution-wait-states.md)的补充证据，尚未调整产品交互。这些检查没有调用外部模型服务。

事件缺少必要字段或对象类型不兼容时，原读取循环只退出并报告断连，会留下原生命令继续执行。现在这种不可继续解析的错误会先阻止新交付、等待已有交付结束，再取消拥有的任务并回收连接，最后报告失败；取消无法确认时保留说明。确定性检查覆盖缺字段、错误字段类型、空属性、非对象事件和取消失败。真实命令树检查先复现、再验证了进程退出及状态持久化；格式错误由测试注入，不代表原生 CLI 自然产生过该事件。普通连接中断与可恢复的流解析异常仍走原有重连路径。

权限和工作流附件切换还存在等待关闭期间的竞争窗口：旧连接被提前移除，新消息可以按旧配置启动。刷新、权限、附件更新与删除现在共用会话变更保护，直到原生连接和必要的 MCP 端点关闭、配置提交后才释放。切换失败保留原配置与连接归属，恢复事件接收并暂停队列；删除期间拒绝新消息。模型目录查询返回后也重新核对会话是否仍存在、后端是否已经改变，避免接受一个无法正确执行的请求。回归先复现这些边界，再通过修复；真实权限切换检查进一步验证了排队请求使用新权限且原生历史保留。

侧栏观察还会与连接关闭重叠：已经开始的历史读取可能被中途关闭，新来的读取也可能调用正在退出的旧适配器。历史读取与连接关闭现在按对话串行化，等待后重新选择连接归属；手动重连与工作流自动交接共用这项处理。服务关闭前等待已有观察结束，关闭开始后不再接受会重新建立连接的观察。确定性检查先复现两种重叠，再验证 Codex、OpenCode、删除和关闭边界；真实 OpenCode 检查确认旧进程不会被侧栏重新拉起，原有子会话仍可读取。
