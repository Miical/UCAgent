
# 测试用例解释编写规范

## 目标

先用简洁的验证目的和验证方法说明用例，再用连续、有序的时间线解释各个技术阶段。读者应能沿着阶段理解为什么需要它、如何实现、谁参与，并追溯到关键赋值或调用及真实源码位置。

解释不绑定 UVM、Verilog、Python 或特定框架。框架名称和源码符号用于定位实现，不能代替系统行为说明。

## 概览

`overview` 保留五个字段，界面默认只显示前两个：

- `purpose`：验证目的，说明要确认的系统行为或问题。
- `method`：验证方法，概括刺激、约束、对照及检查策略。
- `context`：场景与前提，保留参与者、输入和约束的补充背景。
- `mechanism`：核心机制，保留动作如何经过系统并产生结果的补充解释。
- `oracle`：判定依据，保留实际比较或观察的对象及结论边界。

目的和方法各写一段短文，不写运行状态或未经验证的结果。时间线展开具体实现，不逐字重复概览。

## 连续时间线

`timeline` 优先直接按技术阶段排列，例如“准备输入与对照 → 发起请求 → 改变访问条件 → 比较返回结果”。按真实控制流程解释先后、并发或循环；显示顺序不代表并行动作在运行时串行发生。

每个阶段使用以下字段：

- `id`：稳定且唯一的阶段标识。
- `title`：简洁的技术动作，如“固定缓存启用条件”，不要只写类名。
- `description`：该阶段在整个过程中的作用。
- `why`：需要该阶段的原因，或它排除了什么疑问。
- `how`：实际控制、数据流或调用关系。
- `actors`：参与角色；首次出现的源码符号应有角色解释。
- `children`：必要时进一步拆解当前阶段，界面按阅读顺序铺在同一条时间线上，不形成嵌套卡片，也不折叠技术细节。
- `assignments`：关键赋值或调用；`expression` 必须来自真实源码，`meaning` 解释系统作用，`file` 和 `line` 指向实际实现。
- `evidence`：支持解释的源码或运行产物，填写 `kind`、`label`、`path` 及适用的 `line` / `end_line`。
- `expected`：有依据时填写预期观察，不重复目的，也不写成已经通过。

不要重复填写同一句 `description`、`why` 和 `how`；没有新增信息的可选字段留空。已有的单个总问题根节点会在界面中略去，直接展示其子阶段，因此独有的技术信息应放在实际阶段中。

## 语言与证据边界

- 使用简洁的技术语言，先解释角色和系统作用，再引入必要的源码符号；避免口语化标题和没有解释的缩写。
- `confidence=source` 表示源码直接表达的事实；设计动机、因果解释或行为预测属于 `inferred`。混合两类内容时拆开阶段，或将整个阶段标为推断。
- `confidence=observed` 表示有运行产物支持的观察，需要提供可核对的证据；模型填写的标记本身不是验证结果。
- 源码注释可说明作者意图，不能单独证明运行时行为。变量名、配置名和类名也不能单独证明系统结论。
- 证据路径和行号应落在实际实现或直接相关的注释范围内；源码链接打开当前文件，不代表历史运行所用版本。缺少依据时明确保留为推断，不制造引用。
- `status` 和运行记录属于执行信息。只有真实产物支持时才填写 observed / passed / failed，不把解释当作运行证明。
- 正常退出、检查无错误和功能正确是不同结论；覆盖率命中也不证明行为正确。

## 质量检查

1. 能否从目的和方法理解系统问题、刺激方式及判断策略？
2. 时间线是否连续，是否交代了先后、并发及主要参与者？
3. 每个字段是否提供了新增信息，避免与概览或相邻字段重复？
4. 关键赋值和调用是否来自真实源码，位置是否准确？
5. 源码事实、推断和运行观察是否明确区分？
6. 判断方式是否对应目的，是否误把退出码或覆盖率写成正确性证明？
