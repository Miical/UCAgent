# 模块概览编写规范

## 目标

让读者先理解模块负责什么、由哪些功能单元组成，再理解实现机制和关键约束。说明应通用、简洁、技术准确，不绑定验证框架，也不将模块描述成测试流程。

先阅读当前模块及必要的关联源码。名称和注释只能帮助定位，不能单独证明功能或设计动机。

## 栏目与内容边界

固定使用以下顺序，即使内容待完善也保留栏目：

1. **模块职责**：一段短文说明模块解决的问题、输入输出之间的主要关系和边界。不要在这里展开内部细节。
2. **核心结构**：小型结构图，加带项目符号的紧凑说明列表。每项只写“单元名称：一句职责或结构关系”，不展示源码链接、关键代码或多层解释。
3. **子模块**：根据 inspect 返回的 `children` 列出当前配置下的直接子模块，说明各实例在父模块中承担什么职责、与谁配合。使用紧凑项目列表，不只重复模块名；不把孙模块混入当前层级。同类型不同用途的实例分别说明。无直接子模块时由界面明确显示。点击名称可以进入该子模块概览。
4. **工作机制**：解释数据如何存取或转换、控制条件如何配合。必要时展示关键实现代码、代码含义和源码引用。
5. **关键规则**：补充复位、边界、优先级、并发、保持条件和参数约束，避免复述正常路径。
6. **接口与参数**：解释接口角色、协议含义及参数影响。默认值与实例覆写值应明确区分，未解析出的配置不能猜测。

职责讲整体作用；结构讲组成与连接；机制讲如何实现；规则讲限制与边界。每部分应提供新信息，不重复同一段话。不要把模块概览改成连续时间轴。

## 核心结构图

节点数量根据实际实现决定，没有固定四块的模板。简单模块可以只有一个单元，复杂模块可以更多。不要为了数量齐整而拆分、合并或虚构功能。

`structure.nodes` 表示实际功能单元，可对应子模块，也可对应同一模块中的存储、寄存器、控制或数据通路。不应为了凑图而虚构硬件单元。

每个节点包含：

- `id`：本图唯一标识。
- `title`：简短的功能名称。
- `kind`：`block`（逻辑）、`storage`（存储）或 `interface`（接口）。
- `detail`：图内短标签，可标识关键寄存器或信号。
- `text`：图下的一句话职责说明，避免重复信号列表和工作机制。
- `file`、`line`、`end_line`：内部可追溯的源码依据。图下列表不展示这些引用。
- `confidence`：`source` 或 `inferred`；推断还必须在可见文字中明确说明。

`structure.edges` 使用 `from`、`to`、`label` 描述真实的数据或控制关系。端点必须是已声明节点。箭头不是执行先后，不要用流程阶段代替功能单元。保留真实分支、并行、扇出和反馈，不要强行串成链。连接 `kind` 使用 `data`、`control`、`status` 或无法进一步分类的 `relation`；标签简短说明传递的数据或控制含义。

AI 只输出结构语义，不生成位图、SVG、布局坐标或 UI 代码。前端按连接关系自动分层布局，安排反馈连线和标签空间，文字自动换行。简单图居中，复杂图可滚动查看，不强制缩小文字。图下节点不填写展开的 `assignments`；具体实现留给工作机制和关键规则。

`submodules` 使用 `children` 返回的相对 `key` 作为键，简短的用途说明作为值；保存时必须完整覆盖当前直接子模块。`children` 中的模块类型、源码位置与参数可用于核对角色，不能仅凭名称推测功能。无法确认的职责应明确保留为推断或待确认，黑盒不能编造内部实现。核心结构是功能视角，子模块列表是实际实例视角；列表不重复展开机制细节。

## 说明与源码对应

`purpose`、`mechanisms`、`rules`、`parameters` 的说明条目包含 `text` 和源码范围；除职责外，条目使用清晰的 `title`。

工作机制和关键规则参考测试用例的表达方式：

**技术说明 → 关键实现 → 代码含义 → 文件与行号。**

`assignments` 中：

- `expression` 必须是所引用范围中的真实代码，不添加省略号、伪代码或未经读取的调用。
- `meaning` 解释这段代码在系统中的作用，不只是把代码逐字翻译一遍。
- `file` 使用项目内路径，`line` 和可选 `end_line` 使用从 1 开始的真实行号。
- 只选理解机制所需的少量关键片段，不粘贴整个模块。

同一行为不要同时在结构说明、工作机制与关键规则里反复展开。源码引用打开的是当前源码，不能代表某次历史运行所用的版本。

## 事实与推断

`confidence=source` 表示源码直接表达的事实。设计动机、未被源码显式约束的参数要求和因果预测应标记为 `inferred`，并在正文写明“由实现推断”等限定。

混合事实与推断时应拆开说明，或将整条标记为推断。不要添加单独的“源码依据/推断”装饰标签来替代正文中的准确表达。

模块概览是源码解释，不是验证结果。不能从解释、正常退出或覆盖率得出“已验证通过”。

## 标准创建与保存

“生成模块概览”图标打开与测试用例相同的 AI 任务卡，支持悬停预览、点击固定、补充要求及发送任务。任务进入设计总览专属对话，并绑定当前模块实例。

1. 调用 `module_overview(operation="inspect", instance=当前实例)`。
2. 阅读返回的 `guide`、实际源码、现有概览、`schema`、`expected_revision` 和 `source_revision`。本文指导内容质量，返回的 JSON Schema 决定准确字段和限制。
3. 按固定栏目生成完整概览，保留来源与推断边界。
4. 调用 `module_overview(operation="save", instance=同一实例, overview=概览数据, expected_revision=返回值, source_revision=返回值)`。
5. 保存冲突时重新 inspect 后调整，不覆盖其他修改。保存成功后页面自动刷新。

不要直接改 UI 或管理 JSON，不修改 RTL、运行命令或其他模块，不自动运行仿真。应用负责校验源码片段、引用范围、端口、图关系和版本，再保存到项目 `.flowcanvas/module-overviews.json`。

## 展示规范

栏目使用共享标题样式：左侧细短主题色竖线、醒目的标题、底部分隔线和统一间距；测试用例与模块概览一致。内容保持平铺，避免嵌套卡片和花哨配色。小标题应弱于栏目标题。

## 质量检查

1. 是否能快速理解模块职责与主要组成？
2. 图中连接是否有源码依据，是否误画成执行流程？
3. 图下说明是否一项一句，且没有重复机制细节？
4. 机制与规则是否各自提供新增信息？
5. 代码片段、引用范围与接口名称是否真实？
6. 是否明确区分事实、推断和验证结果？
